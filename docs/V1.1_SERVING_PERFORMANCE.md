# AidLens V1.1 — Serving Performance

V1.1 optimizes serving latency without retuning the validated ranking contract.

## Frozen ranking contract

The following remain unchanged from V0.8–V1.0:

- first stage: `BAAI/bge-base-en-v1.5`
- reranker: AidRanker V1
- fusion alpha: `0.50`
- production candidate pool: `40`
- production `top_k`: `10`
- default diversity limit: max 3 passages per evaluation
- Torch remains the production CrossEncoder backend until an accelerated backend passes parity

V1.1 must not change relevance judgments, training data, model weights, or fusion coefficients.

## Why the V1.0 latency sample needed a new baseline

The V1.0 live smoke test reported:

- semantic first stage: 571.431 ms
- AidRanker stage: 2611.017 ms
- internal search total: 3537.886 ms

Two cold-start effects were mixed into that single request:

1. `SentenceTransformerEncoder` was process-lazy and could load BGE on the first semantic request.
2. `AidRankerService._model` was a cached property, so the first rerank included CrossEncoder construction and weight loading.

Also, `total_search_latency_ms` started after query embedding, so it was not an end-to-end request measurement.

## V1.1 phase 1

V1.1 first removed measurement ambiguity:

- one process-local semantic encoder singleton
- one process-local AidRanker singleton
- startup warmup for the semantic encoder
- startup AidRanker warmup when enabled
- configurable Torch batch size and device
- explicit query-encoding latency
- first-stage retrieval latency
- AidRanker inference latency
- internal search latency
- end-to-end route latency
- repeatable live benchmark command with median and p95 summaries

The default AidRanker batch remains 32 and the default device remains automatic selection.

## Warm Torch baseline — 20 August 2026

Seven production-path requests were measured after startup warmup using batch size 32 and the frozen 40-candidate pool.

Median latency:

- client wall: `3048.134 ms`
- end-to-end API request: `3044.851 ms`
- query encoding: `156.004 ms`
- first-stage semantic retrieval: `26.094 ms`
- AidRanker reranking: `2508.859 ms`
- internal search: `2824.393 ms`

P95 latency:

- request: `3379.359 ms`
- AidRanker: `2846.834 ms`

The reranker consumes roughly 82% of median request latency. Warm semantic retrieval is no longer the bottleneck. The first benchmark request had a 684 ms first-stage retrieval outlier; later runs were approximately 20–61 ms, so backend/reranker work remains the priority.

The measured one-time AidRanker model load was `634.989 ms`; removing it from the user request did not materially solve steady-state latency.

## Phase 2 — Torch batch-size sweep

Before adding an accelerated runtime, test whether the 40-candidate pool benefits from a one-pass batch. Batch 32 currently evaluates 32 candidates and then the remaining 8. The deterministic batch benchmark fetches the same 40 semantic candidates once and compares batch sizes 8, 16, 32 and 40 against the frozen batch-32 result.

```bash
docker compose exec api \
  python -m app.perf_cli benchmark-batches \
  --batch-sizes 8,16,32,40 \
  --repeats 3 \
  --output benchmarks/aidranker-v1-batch-sweep.local.json
```

A batch size is eligible only when:

- its raw AidRanker scores remain within the configured numerical tolerance of batch 32; and
- the final fused, diversity-capped top-10 chunk order is identical to batch 32.

The fastest parity-preserving median is selected automatically. Candidate count remains 40 throughout the experiment.

## Accelerated runtime preparation

SentenceTransformers supports Torch, ONNX and OpenVINO CrossEncoder inference. AidLens defines optional API extras for the two accelerated CPU runtimes:

```bash
pip install -e './apps/api[ml,onnx]'
pip install -e './apps/api[ml,openvino]'
```

For Docker builds the equivalent extras can be supplied through `AIDLENS_API_EXTRAS`, for example `ml,onnx` or `ml,openvino`.

ONNX and OpenVINO are not production backends yet. An accelerated runtime may replace Torch only after a same-candidate benchmark demonstrates ranking parity and a meaningful median/p95 improvement.

## Optimization order

1. Warm Torch baseline — completed.
2. Torch batch-size sweep on the same 40 candidates.
3. If Torch remains above the latency target, benchmark ONNX and OpenVINO on the same candidates.
4. Profile candidate-pool cost only after runtime optimization; do not reduce the production value of 40 without ranking-quality evidence.
5. Ship a serving change only after output/ranking parity is checked against the frozen Torch configuration.
